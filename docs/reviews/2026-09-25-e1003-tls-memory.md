# E1003 HTTPS allocation failure

The physical post-publication check of `dev-b19f93b8` found a failed forecast
connection while the cached panel remained valid. USB recovery and the automated
suites passed; those checks did not exercise the ESP32 TLS allocator under its
real task and display load.

## Confirmed cause

An unattended serial capture after reboot reported `mbedtls_ssl_setup returned
-0x008D` for several connections, followed by `ESP_ERR_HTTP_CONNECT` and no HTTP
response. In the pinned ESP-IDF 6.0.2 headers, `MBEDTLS_ERR_SSL_ALLOC_FAILED` is
`PSA_ERROR_INSUFFICIENT_MEMORY`, whose value is -141 (0x8D). This establishes an
allocation failure, not a server HTTP error or certificate rejection.

The E1003 used the default internal-only TLS allocator and a 16 KiB receive
buffer. A post-release state sample showed only a 15,360-byte largest internal
block. The device has 8 MiB PSRAM, already used for its display buffers.
The earlier gzip-buffer reduction alone did not prevent TLS exhaustion.

## Correction

The E1003 board defaults select `CONFIG_MBEDTLS_EXTERNAL_MEM_ALLOC=y`, the
SDK-supported PSRAM allocator. Other boards retain their existing policy.
Certificate validation, TLS record sizes and timeouts are unchanged.
`build.py` rejects a retained E1003 sdkconfig that still uses the old allocation
mode and directs the builder to `--fullclean`. The isolated local USB builder
regenerates its temporary sdkconfig and validates the generated settings too;
it cannot silently retain the old allocator. These regression tests and the
existing installer-manifest tests run in the release pipeline.

This is a board resource-allocation correction; it adds no retry loop, global
state, alternate network client or application-level fallback. It addresses the
strict review's preference for correcting ownership in the canonical layer.

## Verification

The seven build-tool tests and five installer-bundle tests pass. The corrective
release must additionally pass its normal release gates and be exercised on
the connected E1003 with real HTTPS forecast downloads under display/cache
activity. USB responses and a valid cached panel alone are insufficient evidence
of network recovery. Physical and deployment results are recorded in the
corrective pull request so publication does not require another source change.
